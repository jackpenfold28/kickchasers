# Notifications specification

Last verified: 2026-07-23

Source of truth: notification triggers/RPCs in `supabase/migrations/`, `supabase/functions/send-push/index.ts`, `lib/notification-routing.ts`, `lib/local-notifications.ts`, and notification hooks/routes.

## Delivery pipeline

1. A guarded trigger/RPC inserts `notifications`.
2. `call_push_function` reads secrets from `app_internal_settings` and uses `pg_net` to invoke `send-push`.
3. The Edge Function loads `user_push_tokens`, formats copy and badge count, and sends through Expo Push.
4. The app receives in-app rows through Realtime/polling and synchronises the native badge.
5. Tapping a notification resolves a typed route in `lib/notification-routing.ts`.

Direct authenticated notification inserts are revoked. Notification list/count/mark-read functions bind `_uid` to `auth.uid()`.

## Live-game recipients

- Normal official team games notify eligible followers/viewers according to the live-start trigger.
- Team Stats Games use a separate coach/admin recipient path and open the coaches summary.
- No parent-specific notification preference or parent role branch exists.
- The dedupe table `game_live_push_notifications` is service-only.

## Client behavior

- `useRegisterPushToken` runs only on iOS/Android, asks permission, obtains an Expo push token using the EAS project ID, and upserts `(user_id, token)`.
- `useNotificationsRealtime` subscribes to recipient inserts/updates and invalidates notification queries.
- `useNotificationBadgeSync` updates the native badge on app state and notification events.
- Foreground local notification copy covers most core types; server push copy additionally covers live games, team selection, and votes.
- Summary routing replaces the current route when already on a summary to avoid stacking duplicate summary screens.

## Platform status

The implementation is cross-platform at the Expo layer and `app.json` includes the notifications plugin. Repository evidence does not prove APNs/FCM credentials, Edge Function secrets, production deployment, or device delivery. Status is therefore `PARTIAL` operationally even though the application pipeline is implemented.

## Known gaps and risks

- Push dispatch depends on project-specific Edge Function URL and internal settings.
- Foreground/local copy and server copy are separate switch statements and can drift.
- No notification preference centre, quiet hours, per-type opt-out, or parent-specific targeting exists.
- Token registration does not expose an explicit logout cleanup path; stale tokens depend on server/Expo invalidation handling.
- Vote-card reminder generation exists in schema/copy routing, but no repository evidence establishes a scheduled reminder job.
- No automated push/route regression tests exist.
